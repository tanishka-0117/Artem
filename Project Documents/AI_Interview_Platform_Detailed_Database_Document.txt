1. Database Design Goal
The database must act as the application's persistent source of truth for candidate identity, preparation history,
assessment content, interview sessions, coding submissions, progress and recommendations. Feature development
should follow this schema so that the frontend, backend, AI layer and analytics use consistent data.
A major implementation rule is: do not create a new feature first and invent its database fields later. The coding
agent should inspect this document and update the schema intentionally whenever a new requirement requires
new persistence.

Although the supplied schema keeps testCases and solutions under CodingProblem, the execution subsystem
should treat test cases as controlled server-side data. The browser should receive only the information necessary
to solve the problem.

15. Validation Rules
• Required identity fields must not be empty.
• Email must follow the application's validation rules and be unique.
• Enums such as role, difficulty and language should reject unknown values.
• Numeric scores should remain inside defined bounds.
• Reference IDs must point to authorized/existing records.
• Boolean fields such as completed/read should always be normalized.
• Date fields should be stored consistently.
16. Security Rules for Database Access
• User APIs must never expose passwordHash.
• Every user-owned document query must include ownership authorization.
• Admin access must be checked server-side.
• Resume file URLs should be private/signed where required.
• Code submissions should be access-controlled.
• Interview transcripts and AI feedback should only be visible to authorized users.
• Database credentials must remain in backend environment/secrets.
17. Data Lifecycle
Typical lifecycle:
User created → Resume added → Skills extracted → Assessment attempts stored → Interview sessions stored →
Progress summarized → Recommendations generated → Notifications delivered → Candidate re-assesses →
Progress/recommendations updated.

19. Database Rules for the AI Coding Agent
• Read this schema before creating any new feature.
• Reuse the existing entity names and fields where applicable.
• Do not duplicate the same data into multiple collections without a clear reason.
• Keep raw evidence separate from derived summaries such as Progress.
• Use references consistently through userId/problemId and other approved IDs.
• Whenever a feature requires a schema change, update the schema document and affected API/model definitions
together.
• Do not store secrets, API keys or plaintext passwords in MongoDB.
• Do not expose hidden coding test cases through public API responses.
20. Final Database Blueprint
This database supports the complete product flow:
User → Resume → Skill Evidence / Analysis → Interview / Question → CodingProblem → Submission → Progress →
Recommendation → Notification
The goal is to make database design predictable enough that frontend, backend, AI and analytics features can be
implemented without inventing inconsistent models during vibe coding.
Source note: This document preserves the entities and fields supplied in the database requirements. The additional indexing, validation,
