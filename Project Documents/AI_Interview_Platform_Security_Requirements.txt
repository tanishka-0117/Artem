Purpose
Define the mandatory security controls for the web application, AI

Security Principle
Treat every client input as untrusted; enforce security controls at the

Critical Areas
Authentication, authorization, secrets, API security, file uploads, AI calls and
code execution.
1. Security Objectives
• Protect user accounts and authentication credentials.
• Prevent unauthorized access to profiles, resumes, interviews, submissions and analytics.
• Keep AI provider credentials and database credentials outside the frontend.
• Prevent arbitrary user code or commands from reaching the application host.
• Validate all untrusted input before business logic or storage.
• Reduce abuse through rate limits and secure request handling.
• Return only information that the requesting user is authorized to see.
2. Mandatory “Never” Rules

3. Authentication Security
The platform must protect account operations using a secure authentication mechanism such as JWT with
HTTP-only cookies or an equivalent session strategy.
Control
Requirement
Password hashing
Use bcrypt or Argon2; never persist the original password.
JWT authentication
Use signed tokens/session mechanism for protected API access.
HTTP-only cookies
Use where cookies carry authentication tokens so browser JavaScript
cannot directly read them.
Session invalidation
Logout/security events must clear or invalidate the active authentication
mechanism.
Email verification
Verification must use controlled, time-limited tokens/OTP where enabled.
Password reset
Use single-use, time-limited reset tokens.
4. Authorization & RBAC
• Never rely only on frontend route guards or hidden UI controls.
• Every protected backend request must authenticate the caller.
• Every administrative route must verify the caller's role/permission server-side.
• Every user-owned resource must perform an object-level ownership check.
• A candidate must not access another candidate's resume, interview, submission or progress by changing an ID
in the URL.
Example ownership rule:
GET /api/interviews/:id → authenticate user → load interview → verify interview.userId matches authenticated
user → return data.
5. Input Validation
• Validate request body, query parameters, route parameters and uploaded files.
• Reject unexpected fields where strict schemas are appropriate.
• Validate enums such as role, difficulty and coding language.
• Apply limits to text length, arrays and uploaded content.
• Treat resume content and AI-generated/user-provided text as untrusted input.

6. Rate Limiting & Abuse Protection
Rate limiting should be applied especially to operations that are expensive, sensitive or easy to abuse.
Endpoint Area
Recommended Protection
Login / Register
Strict request limits and failed-attempt monitoring.
Forgot/Reset Password
Strict limits to prevent abuse or enumeration.
AI APIs
Per-user/IP quotas and cost-aware rate limits.
Code Execution
Strict request concurrency and execution limits.
File Upload
Upload rate/size restrictions.
General APIs
Reasonable global rate limit with endpoint-specific overrides.
7. CORS
Configure CORS to allow only the intended frontend origins. Do not use unrestricted '*' configuration for
authenticated production APIs when credentials/cookies are involved.
8. Helmet / Security Headers
Use Helmet or equivalent backend security middleware to establish appropriate HTTP security headers. The exact
header policy can be tuned for deployment and frontend needs.
Security headers should complement—not replace—authentication, authorization, validation and secure
application logic.

10. API Request Security
• Use schema validation before controller/business logic.
• Authenticate protected routes.
• Authorize access to the requested resource.
• Return consistent safe error objects.
• Do not expose stack traces, database errors, environment variables or provider responses containing secrets.
• Use secure HTTP transport in production.
11. Secure Error Handling
Client-facing errors should explain what the user can do without exposing internal implementation details.
Unsafe Behavior
Required Alternative
Return raw database exception
Return safe server error message and log internal details.
Return stack trace
Return a generic error reference/message.
Expose provider credentials
Never include secrets in logs or responses.
Reveal whether arbitrary email exists
Use privacy-preserving password-reset responses.
12. Environment Variables & Secret Management
Sensitive values must be stored in backend environment variables or deployment secret management.
Required pattern: DATABASE_URL / MONGODB_URI = backend secret JWT_SECRET = backend secret OPENAI_API_KEY =
backend secret GROQ_API_KEY = backend secret GEMINI_API_KEY = backend secret CLOUDINARY_* = backend secret
EMAIL_PASSWORD = backend secret Frontend receives no provider/API secrets.
Never commit real .env values to GitHub. Commit only a safe .env.example with placeholder names.

13. AI API Security
All AI API calls must happen through the backend.
Secure flow:
Frontend → authenticated backend → AI service/provider adapter → response validation → database/business
logic → frontend
• Do not allow the browser to call OpenAI/Groq/Gemini directly with secret keys.
• Send only the candidate information required for the current AI task.
• Validate structured AI responses before storing or displaying them.
• Apply timeouts and rate/cost controls.
• Do not treat AI output as a security authorization decision.
• Avoid logging sensitive prompts/answers unless required and appropriately protected.

Control
Requirement

15. Database Security
• MongoDB credentials remain backend-only.
• Use MongoDB Atlas controls/credentials appropriate to deployment.
• Do not return passwordHash through user APIs.
• Apply application-level ownership checks for user documents.
• Protect resumes, transcripts, submissions and other private data.
• Avoid logging sensitive tokens or credentials.
16. Logging & Audit Security
Operational logging should support troubleshooting without becoming a source of sensitive-data leakage.
Log
Include
Security events
Timestamp, action, actor reference and safe metadata.
Authentication failures
Enough context for abuse detection without passwords/tokens.
Admin changes
Actor, action and affected resource.
AI failures
Provider/model/operation status without credentials or unnecessary
sensitive content.
Code executor failures
Execution reference and error category, not host secrets.
17. Security Testing
• Attempt unauthorized access to another user's resource IDs.
• Attempt role escalation through modified client requests.
• Test upload restrictions with invalid/oversized files.
• Test rate limits on auth, AI and code endpoints.
• Verify secrets are absent from frontend bundles and API responses.
• Test code sandbox with infinite loops, large memory use and process abuse.
• Verify AI calls cannot be triggered with another user's private context.

18. Secure Request Lifecycle
Incoming Request → HTTPS → Rate Limit → Authentication → Authorization → Input Validation → Business
Logic → DB/AI/Sandbox → Response Sanitization → Client
19. Security Definition of Done
• No plaintext passwords.
• No API keys in frontend code.
• No database credentials in source code.
• Protected APIs authenticate and authorize requests.
• File types/sizes are validated.
• Rate limits are active on sensitive endpoints.
• CORS is restricted to intended origins.
• Helmet/security headers are configured.
• User-submitted code runs only in the isolated executor.
• Sensitive errors are sanitized.
• Security tests for ownership and role bypass pass.
20. Final Security Rule Set
Never expose secrets. Never trust client roles. Never run arbitrary user code on the main application server.
Never let the browser call privileged AI providers directly. Always validate, authenticate, authorize and limit
untrusted input.
The supplied security requirements are treated as mandatory platform rules. This document adds implementation-level structure around
those rules so the security controls can be consistently applied during MERN development and vibe coding.
